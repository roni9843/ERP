# ZATCA e-invoicing (Saudi Arabia)

> Status: **research notes, not implemented.** Always verify against the latest official ZATCA publications (E-Invoicing Implementation Resolution, XML Implementation Standard, Security Features Implementation Standard, Data Dictionary, Developer Portal and SDK) before building. Requirements change, and ZATCA onboards taxpayers in waves.

## Phases

| Phase          | Since                                | What it requires                                                                                                                                         |
| -------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1: Generation  | 4 Dec 2021                           | Issue electronic invoices from a compliant system with the mandatory fields and a QR code on simplified invoices; no tampering, no hand-written invoices |
| 2: Integration | from 1 Jan 2023, in waves by revenue | Generate **UBL 2.1 XML**, sign it cryptographically, and **integrate with the Fatoora platform**: clearance or reporting                                 |

## Invoice types

|            | Standard tax invoice (B2B, B2G)                                                                            | Simplified tax invoice (B2C)                                                            |
| ---------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Flow       | **Clearance**: send to ZATCA, receive the cleared XML (with ZATCA's stamp), _then_ share it with the buyer | **Reporting**: share with the customer immediately, report to ZATCA **within 24 hours** |
| Buyer data | Buyer VAT number and full address required                                                                 | Optional                                                                                |
| QR code    | Required on the visual                                                                                     | Required on the visual (generated by our system)                                        |

Credit and debit notes follow the type of the original invoice and must **reference the original invoice and state the reason**.

## Technical building blocks (Phase 2)

- **EGS unit** (e-invoice generation solution): each device or solution instance that issues invoices is onboarded separately. For us: per tenant, per branch or per POS device.
- **Onboarding**: generate a key pair (ECDSA, secp256k1) and a CSR with ZATCA-specific fields → get an **OTP** from the Fatoora portal → request a **Compliance CSID** → pass the compliance checks (sample invoices) → request a **Production CSID**. CSIDs expire and must be renewed.
- **Each invoice** has a **UUID**; an **Invoice Counter Value (ICV)** that increments per EGS; and the **Previous Invoice Hash (PIH)**, which chains invoices so they cannot be removed or reordered. The invoice hash is SHA-256 over the canonicalized XML.
- **Cryptographic stamp**: an XAdES signature embedded in the UBL XML, signed with the EGS private key.
- **QR code**: TLV-encoded, base64. Phase 1 tags: seller name, VAT number, timestamp, total with VAT, VAT total. Phase 2 adds the invoice hash, ECDSA signature, public key, and (simplified invoices) the stamp signature of the certificate.
- **Validation**: ZATCA validates business rules (BR-KSA-…) such as VAT category codes, totals and rounding consistency, and buyer identification for B2B. Our line-level rounding (`calculateLine`) must match the XML amounts exactly.

## Product rules we will enforce

- An invoice is **immutable once issued**. No edits and no deletion after sending; corrections go through credit or debit notes. Draft invoices stay editable.
- The invoice type (standard vs simplified) is derived from the **client type** (business with a VAT number → standard; individual → simplified).
- Issue date ≤ today; per-EGS sequential ICV; the hash chain is persisted per EGS.
- Keep the signed XML and the ZATCA response (cleared XML, warnings, errors) with the invoice, retained for the statutory period.
- Submission states: `not_submitted → pending → cleared | reported | rejected` (with warnings). Retry transient failures automatically (background job), and surface rejections to the user with ZATCA's messages.

## Planned architecture

```
modules/einvoicing/
├── onboarding/      # CSR generation, OTP exchange, CSID storage (encrypted, per tenant + EGS)
├── xml/             # UBL 2.1 builder from invoice DTOs; canonicalization; hashing
├── signing/         # XAdES signature with the EGS key
├── qr/              # TLV QR generation
├── submission/      # clearance / reporting API client; BullMQ jobs with retries
└── __tests__/       # golden-file tests against ZATCA SDK samples
```

- Secrets (private keys, CSIDs) are encrypted at rest (KMS / envelope encryption) and never logged.
- Use ZATCA's **sandbox / simulation** environments in development and CI. Validate generated XML with the official SDK in tests.
